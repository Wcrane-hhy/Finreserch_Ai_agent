## 〇、先说结论

**一句话**：你要的东西，**参考项目已经替你做过一次筛选**，而且把筛选理由写成了文档。

1. **两个项目的回测引擎是同一套。** Vibe-Research 的 `backtest/` 明确写了"移植自 HKUDS/Vibe-Trading，MIT"，
   还给了移植基线 commit 和逐文件改动清单。所以**不需要读两套引擎**——读一套，而 Vibe-Research
   已经告诉你"该搬哪些、不该搬哪些、为什么"。这是一份现成的迁移蓝图。

2. **Vibe-Trading 不要整体借。** 它 2612 个文件、14 个券商连接器、实盘模块、多智能体团队、
   482 个因子、25 个数据源——那是一个**面向实盘交易的商业产品**。它的工程复杂度和你定的
   "简单、可理解、不为工程感增加抽象"直接冲突。

3. **真正不可替代、值得直接搬的只有 194 KB**：逐 bar 撮合内核 + **A股规则层**
   （T+1 / 涨跌停按前收判 / 100 股整手 / 佣金万2.5低5元+过户费+印花税卖出）。
   `engines/china_a.py` 只有 199 行，但里面每一条规则都是坑，自己写要踩很久。

4. **数据层必须自己写，而且这是项目二真正的新东西。** 参考项目的数据层都接在它们自己的
   凭证/端点体系上（Vibe-Trading 走 tushare 付费 key，Vibe-Research 走它自己的 117 端点注册表）。
   我们已有同花顺 fuyao API + key，实测能拿到完整 OHLCV。**引擎与数据之间只有一条缝**：
   `loader.fetch(codes, start, end) -> {代码: DataFrame}` —— 这条缝自己缝。

5. **有一个必须先做验证、不能后做的事**：你想要的"首板二板三板 / 龙头 / 板块轮动 / 新闻事件"
   这几类策略，需要的数据（涨停板名单、连板高度、板块归属、龙虎榜）**项目一现在一条都没有**。
   这些数据在同花顺 API 里有没有，决定了这几个策略能不能做。**先验证，再定路线**——
   先花两周写好引擎，才发现拿不到涨停数据，等于白做。

6. **项目二不是新项目，是给已有 Tool 注册表加几个 Tool。** 项目一的约定是
   "加 Tool 只改 `tool_registry.py`，不要动 `graph_agent.py`"。回测完全可以按这条走：
   `run_backtest` / `list_strategies` / `get_backtest_result` / `market_review` 四个 Tool 加进注册表，
   Agent 就自然能用。**不引入新框架。**

**Vibe-Trading 的核心架构选择是"Agent 生成策略代码 + 子进程沙箱执行"**：
Agent 往 `runs/<id>/code/signal_engine.py` 写策略代码，然后调 `backtest` 工具，
工具起**子进程**跑 `backtest/runner.py`，用 `Runner(timeout=)` 限时，
还把环境变量**收窄**（不把 LLM key、券商密钥传进生成代码）。
它的仓库里有专门的 `SECURITY.md` 讲这个信任边界。

这是一套很重的设计——**它要防的是"模型生成的代码会做坏事"**。

### Vibe-Research 里有什么

它是 **TS 编排器 + Python 计算/回测** 的双语言结构：

```
orchestrator/src/     174 文件  编排、validator、API、MCP、资料库、报告归档
├── finance/                  A股金融逻辑（阶段/估值/行业/卡口/账本科目/词表…）
├── engines/                  三种引擎模式（codex / deterministic / quick）
└── validator.ts              ← 数字复核：报告里的数字要能复算

backtest/              33 文件  ← 回测（移植自 Vibe-Trading，见下）
calc/                  20 文件  确定性计算库（公式/指标/序列/契约/展示）
datasources/            9 文件  端点注册表（117 端点 / 30 层）+ 健康巡检
.agents/skills/        84 文件  SOP skills（研究流程、取数规范）
knowledge/              2 文件  知识层
providers/              8 文件  模型 provider 模板
```

**它的核心架构选择是不做代码生成**：策略是**写好的 Python 类**
（`strategies.py` 里就三个：`BuyAndHold` / `MaCross` / `RsiReversion`），
Agent 只负责**选策略 + 填参数 + 解释结果**，走 `gate.py`（闸口）→ `run.py` → 引擎。

它还有一条纪律值得注意（`AGENTS.md`，它的"金融研究宪法"）：

> ⛔ **禁止凭记忆生成任何行情 / 财务 / 估值数据。** 每个事实数字必须来自本次运行的取数调用并落盘为证据；
> ⛔ **金额 / 年限 / 比率 / 倍数一律调用 `calc/` 确定性函数计算**，禁止心算、禁止现场手搓公式；
> ⛔ **不给建仓 / 加减仓 / 目标价 / 止损位等任何投资动作建议。**

这三条和你项目一已有的约定**是同一条原则**（"数字必须可追溯"、"失败要明确失败"）。
说明这套价值观不是我硬安的，是这类系统的共识。

## 二、关键发现：两个项目的回测引擎同源

这是本次分析里最重要的一件事。Vibe-Research 的 `backtest/NOTICE.md` 原文：

> 本目录下的**回测引擎**移植自 [HKUDS/Vibe-Trading](https://github.com/HKUDS/Vibe-Trading)，
> MIT 协议。移植基线：上游 `main @ 002373ef...`（2026-08-26）的 `agent/backtest/`。

我做了文件级核对，`backtest/models.py` **字节级完全相同**（3230 B），
`china_a.py` 只差 71 行、`metrics.py` 差 163 行、`constraints.py` 差 36 行。

它对"搬了什么"的清单（**这就是现成的迁移清单**）：

| 类别 | 文件 |
|---|---|
| **原样搬来的（逻辑未改）** | `models.py`（持仓/成交/交易/权益，不可变 dataclass）<br>`constraints.py`（组合约束）<br>`metrics.py`（夏普/卡玛/索提诺/最大回撤/胜率/盈亏比/换手/相对基准）<br>`validation.py` `rebalance_notes.py` `risk_xray.py` `run_card.py`<br>`engines/base.py`（**逐 bar 撮合内核**）<br>`engines/china_a.py`（**A股规则：T+1 / 涨跌停 / 100股整手 / 印花税**）<br>`engines/_market_hooks.py`（代码 → 市场分类）|
| **相对上游的改动（仅两处，均为移除依赖）** | `engines/base.py`：事件(RSSHub)与基本面(Tushare)两路增强改成**惰性 import**<br>`benchmark.py`：删掉 yfinance 兜底，让静默失败出声 |
| **它自己新写的（不属于上游）** | `loader.py`（把取数端点接到引擎——**唯一的新数据代码**）<br>`gate.py`（回测闸口）<br>`run.py`（接线 + 运行期守卫）<br>`strategies.py`（内置策略，也是"策略长什么样"的模板）<br>`tests/`（137 条测试）|
| **它没有搬的** | `loaders/`（25 个数据源）· `optimizers/`（6 个）· 期货/外汇/加密/印度/韩国/越南/期权/composite 引擎<br>`regime.py` `correlation.py` `factor_costs.py` |

**这张表告诉我们的结论**：
Vibe-Research 的 `backtest/` ≈ **Vibe-Trading 减去我们用不上的部分**，剩下 33 个文件，
正好是"一个 A股个人回测系统"需要的全部。移植规模测算：

| | 字节 |
|---|---|
| 拟移植的 13 个文件合计 | **198,355 B ≈ 194 KB** |
| 其中 `engines/base.py` | 81,311 B（撮合内核，最大的一块） |
| 其中 `engines/china_a.py` | **7,828 B**（A股规则，最值钱的一块） |

**194 KB 换一个逐 bar 撮合内核 + A股规则，这是"复用成熟方案"能拿到的最好结果。**

同时提醒一条**法律义务**（不是礼貌）：MIT 许可要求保留版权声明。
移植过来必须带 `LICENSE.upstream` + `NOTICE.md`，并写清改动。
Vibe-Research 就是这么做的，我们照抄这个做法。

## 三、逐层拆解：值得借鉴的东西（按"借法"分四级）

### 第 1 级 —— 直接搬（代码基本不动）

| 来源 | 文件 | 为什么 |
|---|---|---|
| Vibe-Research | `backtest/models.py` | 不可变 dataclass（Position/FillRecord/TradeRecord/EquitySnapshot），117 行，无依赖 |
| Vibe-Research | `backtest/engines/china_a.py` | **A股规则唯一正确性来源**，199 行 |
| Vibe-Research | `backtest/engines/base.py` | 逐 bar 撮合内核，1955 行。自己写要几个月，且写不对 |
| Vibe-Research | `backtest/engines/_market_hooks.py` | 代码 → 市场分类（**要改成只认 A股**） |
| Vibe-Research | `backtest/metrics.py` | 全套指标 |
| Vibe-Research | `backtest/constraints.py` | 组合约束 |
| Vibe-Research | `backtest/validation.py` | 结果校验 |
| Vibe-Research | `backtest/risk_xray.py` | 风险透视 |
| Vibe-Research | `backtest/run_card.py` | 运行卡片 |
| Vibe-Research | `backtest/rebalance_notes.py` | 调仓说明 |

`engines/china_a.py` 里已经处理好的坑（**这些就是自己写会踩的坑**）：

- **T+1**：`can_execute` 里比对 `pos.entry_time.date() == bar_date`，当天买当天卖直接拒
- **不许做空**：`direction == -1` 直接 return False
- **涨跌停按前收判，不按当日收盘** ——源码里有整整一段注释解释为什么：
  用当日收盘算是**未来函数**，两个方向都错（开盘封死但收回来的票被允许成交；
  开盘自由但收盘涨停的票被拒绝成交）
- **100 股整手**：`round_size` 向下取整到 100
- **费用**：佣金万2.5 但有 **¥5 最低**（小资金时这是主要成本）+ 过户费万0.1双边 + **印花税万5 只在卖出**
- **涨跌停带按板块**：主板 ±10% / 双创 ±20%（创业板 2020-08-24 前是 ±10%）/ 北交所 ±30%
- **北交所 2021-11-15 之前直接 raise**（精选层规则未建模）
- **ST 和 IPO 首日不建模**（源码里的原话："ST and IPO exceptions are disclosed, not inferred"）
  → 这一条对我们是个**真实的已知失真**，必须写进回测结果的 limits

### 第 2 级 —— 借思想，自己重写

| 思想 | 出处 | 我们要怎么写 |
|---|---|---|
| **闸口（gate）** | Vibe-Research `gate.py` | 跑之前先判"这次回测成不成立"，只输出 `Plan` 或 `Refusal`，**没有"带警告勉强跑"的第三种** |
| **运行期守卫（_Guarded）** | Vibe-Research `run.py` | 拿到**真实数据**后、出报告前再过一道 |
| **限制随结果走（Result.limits）** | Vibe-Research `run.py` | 回测的限制不是附注，是结果的一部分 |
| **来源可追溯（provenance）** | Vibe-Research `loader.py` | 每根 bar 都能指回原始响应 |
| **策略即目标仓位** | 两家相同 | `generate(data_map) -> {代码: Series}`，取值 -1~1 |
| **策略库持久化** | Vibe-Trading `strategy_store/` | 先用 JSON 落盘；要"策略表现跟踪/衰减"时再上 sqlite |
| **因子库** | Vibe-Trading `factors/` | 做多因子时从 alpha101 里挑几个，**不要 482 个** |
| **量化算法库** | Vibe-Trading `quantlib/` | `performance.py` / `risk.py` / `attribution.py` / `eventstudy.py` 挑着看算法 |
| **数字复核** | Vibe-Research `validator.ts` | 报告里的数字要能复算 —— 和项目一"数字必须可追溯"是同一条 |

**闸口思想值得单独展开**，因为它是这个项目"不做 Demo"的第一个门槛。原文：

> 一个不成立的回测照样能算出夏普和最大回撤，排版整齐、看不出异常。**闸口的价值在拦住。**
> 现在会拦住的：混市场 · A股做T（T+1 表达不了）· 任何市场做T（没有分钟数据）·
> 样本不够 · A股要做空 · 认不出的代码 · 区间反了 · 本金非法或买不起一手。

**为什么这条对我们的价值特别高**：你计划要学的策略里有"做T"这类，
而 A股的 T+1 让"当日买入再卖出"根本不可表达。闸口会在**跑之前**拦住并说清原因，
而不是给你一份看起来正常、实际测的是另一个策略的报告。

**守卫（`_Guarded`）为什么必须单独有一层**：闸口是拿到数据**之前**判的，只能按日历估。
有两件事只有拿到真实数据才知道，而它们都会产出**看着完全正常的报告**：

1. **实际 bar 数不够**（次新股 / 长期停牌 / 数据缺）→ 闸口按日历估"够 480 根"，
   实际只有 200 根，回测照跑完，报告写着"长线"
2. **策略发出了引擎会静默拒掉的信号**（A股做空）→ 引擎只是不成交，
   跑出来的是"删掉所有做空信号后的策略"，**不是你写的那个**

这两条我原样抄，因为它防的正是"报告看起来正常但结论是错的"这一类错误。

### 第 3 级 —— 借做法，不借代码

| 做法 | 出处 | 说明 |
|---|---|---|
| **不搬的诚实清单** | Vibe-Research `NOTICE.md` | 单列"哪些没搬"。我们移植完也要写这个 |
| **策略参数校验要报错** | Vibe-Research `strategies.py` | `MaCross` 里 `fast >= slow` 直接 raise，注释写"参数反了不会报错，只会静默生成一个永不进场的策略" |
| **不许未来函数** | Vibe-Research `strategies.py` | 文件头列了禁止写法：`shift(-1)`、`iloc[-1]` 当常数、用整段序列算分位数再回头用 |
| **`min_periods` 要用满窗口** | Vibe-Research `strategies.py` | 注释："用 `min_periods=1` 的话头几天拿 3 天均线冒充 60 天均线，那是**用一个不成立的指标开仓**，而回测里看不出来" |
| **失败要出声** | 两家都有 | Vibe-Trading 专门有一次提交是"让原本静默的取数失败出声" |
| **停牌 bar 要剔除并报数** | Vibe-Research `loader.py` | "剔了多少要**说出来**——停牌天数本身就是这只票能不能这么回测的判据" |

**关于"代码生成"这个分歧，单独说清楚——这是最容易选错的一步。**

| | Vibe-Trading 的做法 | Vibe-Research 的做法 | 我们选 |
|---|---|---|---|
| 策略从哪来 | **模型现场生成** `signal_engine.py` | **人写好的 Python 类** | 人写 |
| 执行方式 | 子进程 + 超时 + 环境变量收窄 + 沙箱 | 同进程直接调用 | 同进程 |
| 工程量 | 重（`Runner` / `RunStateStore` / 路径安全 / SECURITY.md 信任边界） | 轻 | 轻 |
| 你的第三条要求 | ✗ | ✓ | — |
| 你的第四条要求 | ✗ 黑盒代码你看不懂 | ✓ 每个策略你都读得懂 | — |

理由：
1. **你要"理解策略执行逻辑"** —— 模型现场生成的代码，你第二天看不懂，也改不动。
2. **你要学的策略是"双均线/MACD/SuperTrend"这类经典形态** —— 它们应该是你亲手写的、
   30 行以内、能一眼看完的类，不是模型的黑盒。
3. **沙箱 + 超时 + 环境隔离是 Vibe-Trading 里最重的一块工程**，为一个个人研究工具做这个不划算。
4. **两家的策略契约是一样的**（`generate(data_map) -> {代码: 目标仓位}`）。
   所以将来真想加"让 Agent 生成策略"，**不用改策略层**，只是多一条入口。这是留了门的。

### 4.2 六个必须处理的 gap

#### ① `pre_close` 缺失 —— 最硬的一个坑

**问题**：A股引擎判涨跌停，`BaseEngine.limit_band()` 找的字段名是 `pre_close`。
同花顺日K**没有这个字段**（只有 `open/high/low/close/volume/turnover`）。

**为什么危险**：字段名对不上**不会报错**。上游 `loader.py` 专门写了这条警告：

> 引擎判涨跌停时找的字段叫 `pre_close`，baostock 给的是 `preclose`。名字对不上不会报错
> ——它会**静默回退**到用上一根的收盘价当前收，于是停牌 / 除权那天的涨跌停带算出来是错的。

**处理**：
- datafeed 层主动补 `pre_close` = 上一根 bar 的（复权）收盘价
- **在除权除息日打标记**，写进 `Result.limits`：这些日子涨跌停带可能算错
- 或者：接 baostock（`daily` 接口原生给 `preclose` + `tradestatus`）作为 A股 K线的**第二数据源**，
  同花顺做交叉核对。**这条要你拍板**（见 §6）

#### ② 复权口径没声明

**问题**：实测 `close_price = 76.78571428…`（小数位很长），说明是**按复权因子换算过的**，
但接口没有声明是前复权还是后复权。

**为什么危险**：前复权的历史序列会**随每次除权而重述**——
也就是说同一个日期，你今天跑和三个月后跑，**数字不一样**，回测收益也不一样。
不声明口径，等于报告里的数字不可复现。

**处理**（照抄 Vibe-Research 的做法，它在 `price_basis()` 里写得很清楚）：

> A 股取 baostock 前复权日线（adjustflag=2），不是当日未复权成交价；复权影响不等于分红现金到账。
> 引擎不单独记现金分红、再投资或公司行动现金流。历史序列按本次取数版本重建，
> 可能随公司行动或上游修订重述，并非当时可见快照；不同日期重跑可变，收益偏差方向不作保证。

我们要在 datafeed 层把口径钉死，并把这段话写进每份回测报告。

#### ③ 停牌标记缺失

同花顺日K没有 `tradestatus`。停牌可能表现为**缺 bar**（好处理：`ffill` 有限步）
或**价格不动的 bar**（危险：会被当成"可成交价"）。
Vibe-Research 在 loader 里剔除停牌 bar 并**统计剔了多少**，理由是"停牌天数本身就是
这只票能不能这么回测的判据"。我们要照做。

#### ④ 无指数 / ETF / 板块数据

**后果**：回测报告里的"对照"**只能是等权买入持有这几只标的本身**，不是沪深300/中证500。
这必须像 Vibe-Research 那样**明确标注**：

> 名字叫 benchmark，不说清楚就会被当成沪深300 / 标普 —— 那是完全不同的结论。

Vibe-Research 这块也没接，它如实写了"没接之前，报告里的对照是等权买入持有这几只标的本身，并已如实标注"。
**这是正确的处理方式：能力不足就如实说，不静默用一个错误的东西顶替。**

#### ⑤ ST 股涨跌停没建模

A股引擎对 ST 股会按 **±10%** 算，但 ST 实际是 **±5%**。
上游源码明确写了这是已知不建模项（"ST and IPO exceptions are disclosed, not inferred"）。

**后果**：会**高估** ST 股的可成交性（涨停封死时以为还能买进去）。
**处理**：要么在 datafeed 阶段直接拦住 ST 股，要么写进 `limits`。
我个人倾向**拦住**——ST 股本来也不该是策略研究的主体。

#### ⑥ 北交所与代码规范

- 北交所（43/83/87/88/92 开头）**2021-11-15 之前**的规则未建模，上游直接 raise
- 六位代码 → 交易所后缀要**查表判定，认不出就报错，不猜**。上游 `loader.py` 写得很清楚：
  "猜错的后果是整只票用错市场规则（涨跌停带、T+1、费率全套），而回测结果看着完全正常"
- 必须**核对取回来的确实是那只票**。上游的做法是核对 raw 里落下的 `query.code`，
  并专门写了一条：
  > 🔴 **核对不了 ≠ 核对通过**。一道跑不起来的校验必须报错，不能报成功。

### 4.3 你的策略清单 × 数据可行性（**最需要先确认的一节**）

| 策略想法 | 需要什么数据 | 现在有吗 | 判断 |
|---|---|---|---|
| 双均线 | OHLCV | ✅ 有 | **可做** |
| MACD | OHLCV | ✅ 有 | **可做** |
| SuperTrend | OHLCV（要 high/low） | ✅ 有 | **可做** |
| RSI / 布林 / 动量 | OHLCV | ✅ 有 | **可做** |
| 多因子 | 财务（已有）+ OHLCV + 估值（已有） | ⚠️ 部分有 | **可做**，但需要"全市场横截面"取数，取数成本要解决 |
| 板块轮动 | **板块归属 + 板块行情** | ❌ 未知 | **待验证** |
| 首板 / 二板 / 三板 | **每日涨停名单 + 连板高度 + 封板时间** | ❌ 未知 | **待验证** |
| 龙头策略 | 涨停数据 + 板块归属 + 龙虎榜 | ❌ 未知 | **待验证** |
| 新闻事件策略 | 新闻（已有 search_web/web_fetch）+ 事件到行情的映射 | ⚠️ 半有 | **先做事件研究，不做全自动** |

**这一节的结论决定了项目二的路线**：

- **第一梯队（日线级策略）**：双均线 / MACD / SuperTrend / 多因子 —— 只需要 OHLCV，**现在就能做**。
  而且这几个正好是你列出来要学的。
- **第二梯队（打板类）**：首板二板三板 / 龙头 / 板块轮动 —— **依赖的数据能力尚未验证**。
  必须先做 §7 Phase 0 的数据验证，才知道能不能做、怎么做。

**如果 Phase 0 验证下来同花顺没有涨停/板块数据**，那第二梯队的路线是：
接一个免费 A股数据源（akshare 有 `stock_zt_pool_em` 涨停池、`stock_board_industry_*` 板块数据）。
这属于"复用成熟开源方案"，符合你第二条要求。

   而且缓存、复权口径、来源追溯只有一处要维护。

**一次回测的数据流**：

```
你说一句话："用双均线20/60回测中际旭创2023到2024，本金10万"
   ↓
Agent（LLM）           认出：策略=ma_cross，参数 fast=20 slow=60，标的=300308.SZ，区间=2023-01-01~2024-12-31
   ↓
gate（闸口）           判：A股？代码认得出？区间反了没？样本够不够？要做空吗？本金买得起一手吗？
   ↓                  → 不成立就 Refusal（说清原因 + 补救办法），到此为止，不出报告
   ↓                  → 成立给 Plan
Plan
   ↓
loader → datafeed      取 K线（先查本地缓存，缺的增量补）→ 补 pre_close → 记 provenance
   ↓
_Guarded（守卫）       拿到真实数据后：样本实际根数够吗？策略发做空信号了吗？（引擎会静默拒）
   ↓
Strategy.generate()    返回每只票每天的目标仓位（-1~1，引擎会自己后移一根）
   ↓
ChinaAEngine           逐 bar 撮合：T+1 / 涨跌停按前收判 / 整手 / 佣金印花税 / 拒单记原因
   ↓
metrics                夏普 / 卡玛 / 索提诺 / 最大回撤 / 胜率 / 盈亏比 / 换手 / 对照
   ↓
research/<时间戳>/     落盘 + 生成 report.md（含 limits）
   ↓
Web UI                 实时看：闸口判了什么 / 取了多少根 bar / 每一步在干什么 / 最终报告
```

**注意这条链上"两道门"的位置**：闸口在**取数之前**（只能按日历估），
守卫在**取数之后、出报告之前**（能看到真实数据和真实信号）。
两道门都是为了拦住"报告看起来正常但结论是错的"这种错误。

## 六、迁移计划

**排序原则**：每一步都能**独立验证**，而且**先做"决定路线的事"**。
不要按"从底层往上"的顺序做，要按"从不确定性最高的地方开始"做。

---

### Phase 0 — 只做验证，不写产品代码

**做什么**

1. **验证同花顺 API 的数据边界**（最重要）
   逐个探：交易日历 · 涨停板名单 · 连板高度 · 板块归属 · 板块行情 · 指数行情 · 龙虎榜 · 全市场横截面报价
2. **核对复权口径**
   拿 `300308.SZ` 某个已知日期的复权价 vs 当日实际收盘价，判断是前复权还是后复权；
   再拿一个除权日前后的区间，看序列有没有跳变
3. **验证 `pre_close` 能否用上一根推出**
   找一个真实的除权日，看"上一根收盘"与"当日涨跌停价"的差
4. **决定要不要补第二数据源**（baostock 给 `preclose` + `tradestatus`，免费、无需 key）
5. **确认依赖可装**：`scipy`（指标用）、`pyarrow`（parquet 缓存用）

**产出**：`docs/data-capability.md` —— 一张表：能力 / 有没有 / 端点 / 字段 / 结论

**验收**：§4.3 那 9 个策略想法，**每一个都能对应到"数据够，可做"或"缺什么，路线是什么"**

**为什么排第一**：打板类策略的可行性**完全取决于这一步**。
先写引擎再发现拿不到涨停数据，等于白做。这也符合你"不做 Demo"的要求——
先知道边界在哪，才知道要做多大。

---

### Phase 1 — `datafeed/`：数据层

**做什么**

- `fetch_kline(codes, start, end)` —— 对外唯一接口
- **本地缓存**：`data/market/<代码>_1d.csv`（或 parquet），带 `pre_close` 列
- **增量更新**：缓存里已有的日期不重复取；缺的区间才打 HTTP
- **补 `pre_close`** + 除权日打标记
- **剔除停牌 bar 并报数**
- **`price_basis` 复权口径声明**（每份报告都要带）
- **`provenance`**：每个代码 → 端点 / 行数 / 首末 bar / 停牌数 / 原始响应落盘

**为什么必须有缓存**：项目一的 `get_price_history` 是**每次现取**——
对"读一次给 LLM 看"够用，但回测要**反复读同一段历史**（参数扫描要读几十上百次）。
不缓存就只有两个结果：打爆 API 配额，或者每次回测等几分钟。
**这是项目二第一个真正的新基础设施。**

**验收**
- 同一只票同一区间读两次，**第二次不打 HTTP**（用日志/计数器证明）
- 故意清掉缓存中间一段，能自动只补那一段
- 日志里能看到：取了几根、补了几根、剔了几根停牌

### Phase 2 — `backtest/`：引擎移植

**做什么**

1. 移植 §3 第 1 级那 13 个文件（194 KB）
2. **带上 `LICENSE.upstream` + `NOTICE.md`**（法律义务），NOTICE 里写清搬了什么、改了什么、没搬什么
3. `_market_hooks.py` 改成只认 A股（认不出就报错，不兜底）
4. **自己写 `loader.py`** —— 唯一的新数据代码，实现 `fetch()` 那一条缝，接 `datafeed`
5. **自己写 `gate.py`** —— A股闸口，拦：混市场 / 做T / 样本不够 / 要做空 / 认不出的代码 / 区间反了 / 本金买不起一手
6. **自己写 `run.py`** —— 接线 + `_Guarded` 守卫 + `Result.limits`

**验收**
- 用 `BuyAndHold` 跑一次 `600519.SH` 2022–2024，**指标与手工核对一致**
- 故意给一个做空策略 → 守卫**拦住**（不是静默删掉信号跑完）
- 故意给一个区间只有 30 根日线的次新股 → 守卫**拦住**
- 故意给 ETF 代码（如 `510300.SH`）→ loader **明确报错**（而不是跑出空结果）
- 故意写错代码 `600519.SZ`（后缀错）→ 核对环节**报错**

**不做什么**：不搬 `optimizers/`、不搬其他市场引擎、不搬 `benchmark.py`（没指数数据）

---

### Phase 3 — `strategy/`：策略库

**做什么**

- `base.py` 里把**契约写成文档**：`generate(data_map) -> {代码: Series}`，取值 -1~1
  - 只输出目标仓位；后移一根、归一化、市场规则**都由引擎做，策略里不要重复**
  - 禁止未来函数（写进文件头，像 Vibe-Research 那样列出禁止写法）
- `registry.py` 策略注册表 + **参数 schema**（Agent 要靠它知道有哪些参数、取值范围）
- 策略（按这个顺序）：
  1. `buy_and_hold` —— 基准，**跑不赢它就没有意义**
  2. `ma_cross` —— 双均线
  3. `macd`
  4. `supertrend`
  5. `rsi_reversion` / 布林 / 动量
- **每个策略的测试里必须有"参数配错要报错"的用例**（抄 Vibe-Research 的风格：
  `fast >= slow` 要 raise，理由写在注释里）

**验收**
- `python -m strategy.ma_cross` 能单独跑（不经过 Agent、不经过图）
- 每个策略的参数配错都能报清楚中文错，不静默生成"永不进场"的策略
- 每个策略都有测试，且测试**离线可跑**（沿用项目一测试风格）

---

### Phase 4 — 接进 Agent（复用 Tool 注册表）

**做什么**

- 加 3 个 Tool 到 `tools/`，在 `agent/tool_registry.py` 注册：
  - `list_strategies` —— 列出策略 + 参数说明（Agent 靠它知道有什么可用）
  - `run_backtest` —— 跑一次回测，返回落盘目录 + 摘要
  - `get_backtest_result` —— 读回某次回测的结果
- **不动 `graph_agent.py`**
- **让 Planner 也能看到策略清单**（注册表的通用遍历会自动生效，和加前 9 个 Tool 时一样）

**验收**
- 问："用双均线 20/60 回测中际旭创 2023 到 2024，本金 10 万"
  → Agent 自己选策略、填参数、调 Tool、跑、解释结果
- 问："帮我回测一个 A股日内做T策略"
  → **闸口拦住**，Agent 如实说"T+1 表达不了"（而不是硬跑出一份假报告）
- 问："跑一下我上周那个策略"
  → Agent 找不到就**如实说找不到**，不编一个

**为什么这一步这么轻**：项目一的三层结构（Tool=能力 / Agent=决策 / LangGraph=流程）+
注册表机制，本来就是为这种扩展设计的。**回测是一个"能力"，加进去就行。**

---

### Phase 5 — 参数验证 + 风险分析（"不做 Demo"的门槛）

**做什么**

- **参数扫描**：网格 + 结果可视化（哪个参数区间稳定、哪个是尖峰）
- **样本外切分**：训练段 / 测试段，避免参数在整段历史上调优
- **多重检验提醒**：试了 200 组参数挑出最好的，那不是发现，是**运气**——
  必须显式报告"试了多少组"（Vibe-Trading 的 `quantlib/multipletesting.py` 就是干这个的）
- **风险透视**：最大回撤区间 / 回撤持续时长 / 连续亏损笔数 / 盈亏比分布
- **对照**：等权买入持有（明确的降级方案，标注"这不是指数"）

**为什么单独一期**：**只跑一次回测得到的好看曲线，几乎一定是过拟合。**
一个"能长期使用的个人工具"必须能回答"这个结果是运气还是规律"。
这一期就是那条分界线——**没有 Phase 5，前面都只是 Demo。**

**验收**
- 跑一次参数扫描，报告里明确写出"扫描了 N 组，最优组的样本内/样本外表现"
- 能给出"这个策略在什么参数区间是稳定的"这类结论，而不只是"最优参数是 X"

### Phase 6 — 每日复盘（收盘后自动跑）

**做什么**

- **全市场取数**：收盘后拉当日行情 + 涨停/连板数据（依赖 Phase 0 的验证结果）
- **策略库批量跑**：对股票池跑一遍，输出"符合条件股票"
- **市场环境分析**：涨跌家数 / 涨停家数 / 连板高度 / 板块强弱
- **生成今日复盘报告**：写到 `research/<日期>/daily_review.md`
- **定时任务**：收盘后自动触发（用系统的定时能力）

**验收**
- 手动跑一次，生成一份结构完整的今日复盘
- 设成定时任务，第二天自动生成

**注意**：这一期**依赖 Phase 0 的数据验证结论**。
拿不到涨停/板块数据的话，这一期就只能做"涨跌家数 + 策略信号"这一半。

### Phase 7 — Dashboard 统一

**做什么**

- 把 `web_ui.py` + `web/index.html` 扩成 4 个入口：
  1. 公司研究 Agent（项目一已有）
  2. 策略回测（跑回测 + 看净值曲线 + 逐笔成交 + 参数扫描热力图）
  3. 每日复盘（看当日报告）
  4. AI 金融问答（简单对话）
- **复用已有的 SSE 机制和节点点亮逻辑**，不引入前端框架

**验收**
- 4 个入口都能用；回测页能实时看到"闸口 → 取数 → 守卫 → 引擎 → 落盘"的过程

## 八、"不做 Demo"的三个门槛

你说"不要做一个简单 Demo，希望最终成为真实可长期使用的个人工具"。我把这句话翻译成三条可检验的标准：

1. **结果可复现**：同一份数据、同一组参数，今天跑和明天跑的结果一样。
   → 需要复权口径声明 + 数据落盘 + 参数记录。（Phase 1、2）
2. **不成立就说出来**：数据不够、规则不适用、信号会被静默拒掉 —— 都要**在出报告之前**拦住，
   而不是给一份看起来正常的报告。（Phase 2 的两道门）
3. **能回答"是运气还是规律"**：跑一次回测得到好看曲线没有意义，
   要能说清"扫了多少组参数、样本外怎么样、这个结论稳不稳"。（Phase 5）

**没有第 3 条，前两条做得再好也只是个 Demo。**

## 九、风险与已知限制（提前写下来，不藏在心里）

| 风险 | 后果 | 应对 |
|---|---|---|
| 同花顺 API 有配额/限流 | 全市场取数（多因子、每日复盘）可能打不动 | Phase 1 的缓存是**必需品**，不是优化 |
| `pre_close` 靠上一根推 | **除权日涨跌停带算错** | 除权日打标记写进 limits；或补 baostock |
| 复权序列会重述 | 历史数字随公司行动变化，不可复现 | 口径声明 + 原始响应落盘 + 记录取数日期 |
| ST 股 ±5% 未建模 | **高估** ST 股可成交性 | 拦住 ST 或写进 limits |
| 无指数/板块数据 | 对照只能是"等权持有这几只标的本身" | 明确标注"这不是指数"，不静默顶替 |
| 打板类数据未验证 | 第二梯队策略可能做不了 | **Phase 0 先验证** |
| 自己写的 loader 有 bug | 会产出"看着正常"的错误结果 | 移植过来的引擎有 137 条上游测试思路可参考；我们要照项目一风格把测试补上 |
| 参数过拟合 | 回测好看、实盘亏钱 | Phase 5 是第一优先级，不是可选项 |

**一条最需要记住的**：这个系统里最危险的错误**不是程序崩溃**，而是
**一份排版整齐、指标齐全、看不出异常的错误报告**。
两个参考项目里几乎每一条注释都在防这一类错误——
"字段名对不上不会报错"、"零成交的报告看起来很正常"、"静默回退"、"静默拒单"。
**移植时那些看起来啰嗦的中文注释，是这套代码最值钱的部分，不要删。**
